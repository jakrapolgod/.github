# Analysis and Design of Algorithms

code ที่ "รันได้" ไม่เท่ากับ code ที่ "ถูก" และ code ที่ถูกก็ยังไม่แน่ว่า "เร็วพอ"
วิชานี้มีไว้ตอบ 3 คำถามกับทุก code ไม่ว่าคนหรือ AI เขียน:

1. **ถูกไหม** — พิสูจน์ได้อย่างไร และหาตัวอย่างที่ทำให้ผิดได้อย่างไร
2. **ถ้าผิด จะแก้อย่างไร** — ระบุสาเหตุให้ได้ระดับความคิด ไม่ใช่แค่ปะ code
3. **ถ้าถูก มีประสิทธิภาพแค่ไหน** — Big-O เทียบกับขนาดข้อมูลจริง และจะปรับให้ดีขึ้นอย่างไร

ห้ามถือว่าคำตอบเสร็จ จนกว่าจะตอบครบทั้งสามข้อด้วยหลักฐาน (ผลการรัน) ไม่ใช่ความมั่นใจ

## ขั้นตอนบังคับ

ทำตามลำดับนี้ทุกครั้ง ข้ามขั้นไม่ได้

### 1. สเปกโจทย์ (Specification)
- เขียน input / output ให้ชัด และ **ข้อจำกัด** (เช่น `n ≤ 2·10^5`, ค่าติดลบได้ไหม)
- คำนวณงบเวลา: ถ้า `n = 2·10^5` และ Python ทำได้ราว `10^7` คำสั่งต่อวินาที
  → ต้องการ `O(n log n)` หรือดีกว่า; `O(n²)` = `4·10^10` ไม่ผ่าน
- ลิสต์ **edge case** ก่อนเขียน code: ว่าง, ตัวเดียว, ค่าซ้ำทั้งหมด, ค่าติดลบทั้งหมด,
  ค่าสูงสุด/ต่ำสุด, ไม่มีคำตอบ, กราฟไม่เชื่อมต่อ ฯลฯ

### 2. Brute force อ้างอิง (Reference)
- เขียนวิธีที่ช้าแต่ "ถูกแน่นอน" ตรงตามนิยามโจทย์ (ลองทุกกรณี)
- สั้นที่สุด อ่านง่ายที่สุด ไม่ต้องเร็ว — หน้าที่ของมันคือเป็นกรรมการ

### 3. ออกแบบวิธีที่มีประสิทธิภาพ (Design)
- บอกเทคนิคที่ใช้: greedy, divide & conquer, dynamic programming, graph search,
  two pointers, binary search on answer, ฯลฯ
- ถ้าใช้ **greedy** ต้องมีข้อพิสูจน์ (exchange argument) หรือ counterexample search
  เพราะ greedy คือจุดที่ code จาก AI ผิดบ่อยที่สุด

### 4. เหตุผลความถูกต้อง (Correctness)
อย่างน้อยหนึ่งอย่าง เขียนไว้ใน docstring/comment ของฟังก์ชัน:
- **Loop invariant** — initialization / maintenance / termination
- **Recurrence ของ DP** — นิยาม state, transition, base case, ลำดับการคำนวณ
- **Exchange argument** สำหรับ greedy
- **Induction** สำหรับ recursion

### 5. วิเคราะห์ความซับซ้อน (Complexity)
- Time และ Space ในรูป Big-O พร้อมที่มา (นับ loop / แก้ recurrence / Master theorem)
- เทียบกับงบเวลาในขั้นที่ 1 ว่าผ่านหรือไม่

### 6. ทดสอบ (Verification)
- **ตัวอย่างจากโจทย์** + **edge case** จากขั้นที่ 1 เป็น assert
- **Stress test**: สุ่ม input เล็ก ๆ หลายพันชุด เทียบผลกับ brute force
  ถ้าต่างกัน ให้พิมพ์ input ที่ทำให้ผิด (counterexample) ออกมา
- รันจริงทุกครั้ง แล้วรายงานผล — ห้ามบอกว่า "ถูก" โดยไม่ได้รัน

### 7. วัดประสิทธิภาพ (Benchmark)
- จับเวลาที่ขนาด input เพิ่มขึ้นเป็นเท่าตัว ดูว่าเวลาโตตามที่ Big-O ทำนายไหม
  (`O(n)` → ×2, `O(n²)` → ×4, `O(n log n)` → ×2 นิดหน่อย)
- ทดสอบที่ขนาดสูงสุดของโจทย์ว่าอยู่ในเวลาที่กำหนด

## โครงสร้างไฟล์บังคับ

ทุกไฟล์อัลกอริทึมต้องมีส่วนเหล่านี้ตามลำดับ (ดูตัวอย่างเต็มที่ `template.py`):

```python
"""
โจทย์: ...
Input / Output: ...
ข้อจำกัด: ...  → งบเวลา: O(...)
Edge cases: ...
"""

    ...

def solve(...):            # [3][4][5] วิธีจริง
    """
    เทคนิค: ...
    ความถูกต้อง: (invariant / recurrence / exchange argument)
    Time: O(...)  เพราะ ...
    Space: O(...) เพราะ ...
    """
    ...

def test_examples():       # [6] ตัวอย่าง + edge case
    ...

def stress_test(trials):   # [6] สุ่มเทียบกับ brute_force
    ...

def benchmark():           # [7] วัดเวลาที่ n โตขึ้นเป็นเท่าตัว
    ...
```

โจทย์แบบแข่งขันที่อ่านจาก stdin ให้แยก `main()` ที่อ่าน/เขียน I/O ออกจาก `solve()`
เพื่อให้ `solve()` ทดสอบได้โดยตรง และใช้ `sys.stdin.buffer` เมื่อ input ใหญ่

## เมื่อตรวจ code ที่ได้จาก AI (หรือคนอื่น)

รายงานในรูปแบบนี้:

1. **ผลการทดสอบ** — ผ่าน/ไม่ผ่าน พร้อม counterexample ที่เล็กที่สุดที่หาได้
2. **สาเหตุ** — ผิดที่ความคิดตรงไหน (เช่น "greedy เลือกเหรียญใหญ่สุดไม่ optimal
   เมื่อชุดเหรียญไม่ใช่ canonical") ไม่ใช่แค่ "บรรทัด 12 ผิด"
3. **ความซับซ้อน** — Big-O ของ code เดิม และผ่านข้อจำกัดหรือไม่
4. **วิธีสั่งให้ AI แก้** — เขียน prompt ที่ระบุ counterexample, สาเหตุ,
   และเทคนิค/Big-O ที่ต้องการ เช่น
   > "code นี้ให้ 3 สำหรับ coins=[1,3,4], amount=6 แต่คำตอบคือ 2 (3+3)
   > greedy ใช้ไม่ได้กับชุดเหรียญนี้ ให้เขียนใหม่เป็น DP แบบ bottom-up
   > O(amount·len(coins)) พร้อม brute force และ stress test"
5. **code ที่แก้แล้ว** ตามโครงสร้างบังคับข้างบน และผลการรันจริง

## สิ่งที่ห้ามทำ

- ห้ามส่ง code ที่ไม่มี brute force และ stress test สำหรับโจทย์อัลกอริทึม
- ห้ามอ้าง Big-O โดยไม่บอกเหตุผล
- ห้ามบอกว่า "ถูกต้อง" หรือ "เร็วพอ" โดยไม่มีผลการรันประกอบ
- ห้ามใช้ greedy โดยไม่พิสูจน์หรือไม่ stress test
- ห้ามแก้ bug ด้วยการเพิ่ม `if` เฉพาะ test case ที่พัง — ต้องแก้ที่ความคิด
